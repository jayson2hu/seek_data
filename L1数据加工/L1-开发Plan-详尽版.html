开发 Plan · L1 数据加工 · 详尽版

L1 数据加工 — 详尽开发计划

把 L1 拆成 10 个 EPIC、约 30 个小功能，每个含子任务、验收标准、自测。L1 可独立并行开发：对着 L0 契约 stub + fixtures 即可全流程跑通与验收，集成时无缝对接。核心信条：与垂直无关、算一次、全局复用。

范围：仅 L1（清洗+初评+基础分析+向量） EPIC：10 个 小功能：~30 个 预估：~17 人日 栈：Python · LangGraph · PG/pgvector

i文档说明与范围

本文档只覆盖 L1（数据加工）。L1 消费 L0 产出的内容，做与垂直无关的通用理解（摘要/观点/金句/实体/向量/基础标签），产出给 L2/L3。

结构：EPIC → Feature（可独立交付验收）→ 子任务。每个 Feature 配 验收标准 与 自测。MUST = MVP 必需，SHOULD = V1 完善。

⇄并行开发与契约（交给 Codex 的关键）

L1 与其他层同时开发，因此必须靠"契约"解耦——L1 不等 L0 完成即可开工与验收。

⬇ 输入契约（来自 L0，可 stub）

  • 事件 content.ingested {content_id, lang}
  • 查询 get_content(id) -> {id, clean_text, lang, title, source, ...}
  • standalone 开发：用 L0ContentProvider 的 stub 实现 + fixtures 喂内容，无需真 L0

⬆ 输出契约（给 L2/L3）

  • 产物表 content_base_analysis（结构稳定）
  • 事件 content.analyzed {content_id}
  • 状态推进 WAIT_ANALYSIS → WAIT_SCORE / CANCELLED
统一集成的接缝：① 共享 DB（L1 拥有 content_base_analysis / enrichment_cache 表，只读 content_items）；② 共享事件主题（订阅 content.ingested，发 content.analyzed）；③ 共享 content.status 状态机。只要 L1 严守这三个接缝，集成时改一个 ContentProvider 实现（stub→真 L0）即可。

▤数据库 DDL（L1 拥有的表）

-- L1 产物（与垂直无关，算一次）
CREATE TABLE content_base_analysis(
  content_id BIGINT PRIMARY KEY REFERENCES content_items(id),
  one_liner TEXT, summary TEXT,
  key_points JSONB DEFAULT '[]', quotes JSONB DEFAULT '[]',
  entities JSONB DEFAULT '[]', base_tags JSONB DEFAULT '[]',
  embedding vector(1536), lang TEXT,
  model TEXT, graph_version TEXT,
  tokens_in INT, tokens_out INT, cost NUMERIC(10,5),
  created_at TIMESTAMPTZ DEFAULT now());
CREATE INDEX ON content_base_analysis USING ivfflat (embedding vector_cosine_ops);

-- 幂等/重放缓存
CREATE TABLE enrichment_cache(
  content_hash TEXT, graph_version TEXT,
  result JSONB, created_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY(content_hash, graph_version));
表归属清晰（便于统一）：L1 只写 content_base_analysis / enrichment_cache，只读 content_items（L0 拥有）。集成时 schema 自然合并，无冲突。

✓测试策略

单元测试

  • 纯函数：清洗、分段、schema 校验、标签映射、成本计算
  • 无 LLM、无 IO，mock
  • 覆盖率 ≥ 80%

图测试（FakeLLM）

  • 用 FakeLLM / 录制回放 提供确定性响应
  • 对 fixture 内容跑整图，断言结构化产物
  • 零成本、可重复，进 CI

质量 / 金标

  • 金标集：人工标注摘要/实体，离线评估准确率
  • 过滤准确率、抽取覆盖率阈值
  • 真模型仅离线评估，不进 CI
# fixtures
tests/fixtures/content/{normal_en,normal_zh,long,marketing_lowquality}.json
tests/fixtures/llm/*.json         # FakeLLM 预设响应/cassette
tests/golden/{slug}.json          # 摘要/实体金标
# 运行
uv run pytest -m unit
uv run pytest -m graph             # FakeLLM，确定性
uv run pytest --cov=enrichment_graph
关键：LLM 节点必须可确定性测试。用 FakeLLM 注入预设响应（或录制真实响应回放），让 CI 不真调模型、不花钱、结果稳定。真模型质量用离线金标集单独评估。

★L1 总验收（Definition of Done）

  • 独立可跑：用 L0 stub + fixtures，无需真 L0 即可端到端跑通并验收
  • 初评：低质/营销内容被正确剔除（CANCELLED），不进深加工
  • 抽取：one_liner/summary/key_points/quotes/entities 严格符合 schema、与原文一致
  • 长文：分段聚合不遗漏要点
  • 向量/标签：embedding 入 pgvector，标签与垂直无关
  • 产物契约：content_base_analysis 完整；content.analyzed 不丢不重；状态正确流转
  • 成本：模型分级生效，单篇成本可控、可统计、超阈告警
  • 幂等/重放：缓存命中省成本；版本升级可重放
  • 质量：单元+图测试覆盖率达标，CI 全绿（不真调模型）
达成即：L1 可作为独立、确定性可测、成本可控的内容加工服务，向 L2 稳定供给"内容知识"。集成时仅把 ContentProvider 从 stub 换成真 L0。
